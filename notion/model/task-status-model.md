# Task 상태·Actor·Blocker 모델

## 선택한 구조

Pilot A는 Task Status를 6개로 제한한다.

- 상태: 진행 단계
- 현재 Actor: 다음 행동 또는 응답을 수행해야 하는 주체
- Blocker: 다음 상태 전이를 막는 구체적 원인

`내부 확인 대기`, `외부기관 대기`, `GP 회신 대기`를 각각 Status로 만들지 않고 `TS-WAIT`와 Actor로 표현한다. 상태 폭증과 View 중복을 막으면서 대기 대상을 검색할 수 있기 때문이다.

## Actor 정의

| Actor ID | 표시값 | 의미 | 예 |
|---|---|---|---|
| ACT-OPS | 운영팀 | 업무정보·판단을 제공해야 함 | 조합 기본정보 제공 |
| ACT-SUPPORT | 지원팀 | 행정 Task를 수행하거나 검수해야 함 | 서류 준비·접수 |
| ACT-MANAGER | 관리역 확인 | 담당 관리역의 명시적 확인이 필요함 | 계좌 유형 승인 |
| ACT-GP | GP | GP의 회신·날인·자료가 필요함 | 재날인본 회신 |
| ACT-EXTERNAL | 외부기관 | 세무서·은행 등의 처리·회신을 기다림 | 접수 처리·은행 심사 |

`현재 Actor`는 RACI의 최종 책임자 전체가 아니라 바로 다음 행동 또는 응답 주체다. 외부기관 대기 중 지원팀은 추적 담당자이지만 Current Actor는 `외부기관`, 다음 Action에는 지원팀의 재확인 시점과 행동을 기록한다.

## Blocker 운영방식

Pilot A는 별도 Blocker DB나 신규 유형 Property를 만들지 않고 **A+D 혼합안**을 사용한다.

- `Blocker` Text: `[유형] 원인 / 발생주체 / 해결책임자 / 발생일 / 목표해결일 / 해결조건 / 현재결과`
- `Task 상태`: 막힘의 진행 단계(`대기` 또는 `보완`)
- `현재 Actor`: 해소를 위해 응답·행동할 주체
- `다음 Action`: 지원팀이 수행할 재확인·Escalation

해소 시 Blocker를 삭제하지 않고 끝에 `해소일 / 해결결과 / 해소자`를 추가하고 Status를 전환한다. 별도 Blocker DB는 반복·다중 Blocker와 감사 추적 필요성이 Pilot에서 확인될 때 Post-Pilot로 검토한다.
